# Security notes

How StockAche protects data, and the limits worth knowing about.

## Secrets and keys

| Key | Where it lives | Safe in the browser? |
| --- | --- | --- |
| Supabase publishable key | `frontend/.env`, Netlify, Render | Yes, by design |
| Supabase secret key | `backend/.env`, Render only | **No**: it bypasses all database access rules |
| Django `SECRET_KEY` | `backend/.env`, generated by Render | No |
| Database password | inside `DATABASE_URL` on Render | No |

- `.env` files are gitignored; the `.env.example` files document every variable.
- Only `VITE_`-prefixed variables reach the browser bundle. Never put a secret
  behind that prefix.
- Image uploads go through Django precisely so the secret key never needs to
  reach the browser.

If a secret key is ever exposed (pasted somewhere, screenshotted, committed),
rotate it: **Supabase → Project Settings → API Keys**, revoke the secret key,
and update `SUPABASE_SERVICE_KEY` wherever it is set. Legacy JWT keys stay
valid until explicitly disabled under *Legacy keys*; revoking the new-format
key alone does not invalidate them.

## Database access

Supabase publishes every table in the `public` schema through its REST API,
and by default the publishable key can read and write them. Since that key
ships in the frontend, those tables would effectively be public.

`backend/core/db_security.py` closes this. After every `migrate` it enables
row-level security on each table Django owns. With no policies defined, the
publishable key can neither read nor write any of them. Django connects as
the tables' owner, which row-level security does not apply to, so the
application is unaffected. Tables added by future migrations are covered by
the deploy that creates them.

## Server-side rules

Business rules are enforced in Django, not the browser: MOQ, stock, order
status transitions, commission, ownership checks and identity documents. A
crafted request cannot skip them.

## Payments

Card details are collected in browser memory for the simulated checkout and
discarded. The server receives only a payment method and an amount, which
keeps the system out of PCI scope. Keep it that way when integrating a real
gateway: use the gateway's hosted page rather than accepting card data.

## Development login

`ENABLE_DEV_LOGIN=True` exposes `POST /api/auth/dev-login/`, which issues a
session for any seeded account **without a password**. It exists for local
testing only; no part of the UI uses it. It must be `False` anywhere reachable
from the internet. `render.yaml` sets it to `False`, and a deploy check
(below) fails if it is on while `DEBUG` is off.

## Automated guards

**Secret scanner**: `scripts/check_secrets.py` looks for Supabase secret keys,
service-role JWTs, Google OAuth client secrets, private keys and Postgres URLs
containing a password. Placeholders such as `<db-password>` are ignored.

```bash
python scripts/check_secrets.py               # scan the repository
python scripts/check_secrets.py --install-hook  # block such commits locally
python scripts/check_secrets.py --self-test   # verify the detection rules
```

**Deploy checks**: `python backend/manage.py check` fails when:

| Check | Condition |
| --- | --- |
| `stockache.E001` | A secret key appears in `frontend/.env`, where it would ship to browsers |
| `stockache.E002` | `ENABLE_DEV_LOGIN` is on while `DEBUG` is off |
| `stockache.E003` | `DJANGO_SECRET_KEY` is still a development placeholder in production |

## Known limitations

- **Uploaded files rely on unguessable URLs.** Listing photos and identity
  documents share one public Supabase Storage bucket. Each file gets a random
  UUID as its name, and a document's URL is only returned to its owner and the
  admin, but anyone who obtains a URL can open the file. A private bucket with
  short-lived signed URLs would be the stronger design for identity documents.
- **The Django admin is publicly reachable** at `/admin/` on the API host.
  Use strong passwords for superuser accounts.
- **Payments are simulated.** No real money moves until a live gateway is
  integrated.
